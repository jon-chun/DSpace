  run the tests (the brief says not to), and nothing was written in the clone.

  What I found:
  - Crash boundaries and orphans (probe 6): a file's bytes are written to
    storage before the database commit, inside the caller's transaction. If that
    transaction rolls back or crashes, the file stays on disk with no database
    row. The cleanup command only walks rows marked deleted=true, and nothing
    scans storage for unreferenced files, so these orphans are never found. No
    test covers an interrupted ingest; tests do cover an interrupted storage
    migration (BitstreamStorageServiceImplIT) and an interrupted checker run
    (ChecksumCheckerIT).
  - Fixity: MD5 only, fixed in code. Storage keys are random, not derived from
    content. The checker command compares each file with the digest recorded at
    ingest, oldest check first. A mismatch is recorded and emailed to the
    administrator, and nothing else happens. A missing file is set to
    to_be_processed=false and is skipped by every later run. DSpace has no
    built-in schedule for the checker and no REST route for it. No test drives a
    real mismatch through the checker.
  - Event record: nothing is append-only or hash-chained.
    - The audit log goes to a Solr search index and is off by default. Its
      events are sent before the database commit, and a failed write is logged
      and ignored.
    - Provenance is a free-text metadata field.
    - Versioning copies the whole item.
  - Standards: METS packages carry file digests. PREMIS appears only as version
    1.0 object metadata, not as events. I found no OCFL, and BagIt is only named
    in a SWORD dummy server.
  - Derivatives: extracted text and thumbnails differ from originals only by
    bundle name. Each is linked to its source by a derived file name.

  The three claims I'm least sure of:
  1. I inferred that a "mark as deleted first" step in the store code no longer
     protects a crashed write, because it now runs in the same uncommitted
